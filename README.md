# Known to Done · KTD

从具体困惑出发，让知识逐步成为自己的理解、判断与行动能力。

## 为什么做 KTD

面对陌生问题，我们通常只能从已经知道的地方提问。一个具体困惑可能关联更大的知识领域，但我们未必知道它叫什么，也未必理解两者之间的联系。

即使接触到相关理论，仍可能缺少从具体经验理解抽象概念的路径。探索不断扩展，真正作出判断、尝试行动和接受反馈的机会却迟迟没有出现。

KTD 希望借助 AI，帮助人发现原本看不到的相关知识，补齐理解所需的中间联系，并在适合的情境中通过实践修正认识。

## 共同目标

**帮助人从自身能够描述的问题出发，发现相关知识、建立有依据的理解，并通过独立判断与实践反馈，逐步形成可迁移的能力。**

这一目标包含四个相互联系的方向：

- **发现**：看见原本不知道的概念、领域和解释视角，找到值得继续了解的问题。
- **理解**：把抽象概念与具体经验连接起来，知道一种理论解决什么问题、为何适用、边界在哪里。
- **判断与行动**：结合具体条件形成自己的判断，在认识尚不完整时选择适当的尝试。
- **反馈与修正**：比较预期与实际结果，修正解释和做法，积累能用于新情境的经验。

这些方向可以反复往返。实践会带来新的困惑，新的认识也会改变下一次实践。

## 设计原则

**1. 从用户的具体问题进入。**

允许用户带着模糊感受、局部经验或一个陌生名词开始。帮助澄清真正关心的事，保留原问题中的条件与意图。

**2. 把理解所需的联系讲出来。**

从具体问题走向抽象概念时，解释每一步为什么相关。让用户看到概念如何帮助理解原问题，并能沿着这条联系继续思考。

**3. 扩展视野，同时保持可选择的范围。**

展示重要的相邻视角，说明各自能回答什么。根据当前困惑决定展开程度，使用户能够选择下一步，也能够停在本次已经获得的理解上。

**4. 支持用户形成自己的判断。**

AI 提供解释、证据、候选路径和反馈，让判断依据可以被理解、质疑与修正。需要用户思考时，留出思考空间；已有信息足以推进时，直接提供帮助。

**5. 让认识有机会接受现实检验。**

当目标涉及应用或解决实际问题时，把重要判断连接到可观察的结果。允许根据风险与条件进行小步尝试，再用反馈调整认识。一次知识定位也可以以找到方向为完成标志。

**6. 每个 Skill 承担清楚的职责。**

围绕一种可复用的认知操作设计入口、工作方法和完成标准。每个 Skill 能独立产生价值，需要时再衔接其他能力；具体交互方式由它所解决的问题决定。

**7. 用真实使用检验效果。**

区分事实、推断与待验证的解释，随着新证据更新结论。改进 Skill 时，检查它是否帮助用户理解关系、作出判断或完成尝试，并关注是否增加了额外的使用负担。

## 怎样判断 KTD 有帮助

根据当次任务，检查用户是否获得了具体的进展，例如：

- 能说出一个原本不知道、且与问题确实相关的探索方向，并解释相关性。
- 能用自己的话解释一个概念如何回应具体问题，以及它的适用条件。
- 能基于证据比较候选解释或方案，知道还缺少什么信息。
- 能完成一次适当的尝试，并根据结果修正原有判断。

每个 Skill 按自己的职责确定完成标准；整套 KTD 的长期价值体现在用户独立理解、判断和行动能力的增长。

## 目录与使用

```text
known-to-done/
├── README.md
└── skills/
    ├── ktd-locate/
    │   └── SKILL.md
    └── ktd-reconstruct/
        └── SKILL.md
```

Skills 统一使用 `ktd-` 前缀，每个 Skill 的必要执行要求保存在自己的 `SKILL.md` 中，可独立使用。

将仓库克隆到本机后，在公共 Skills 目录中建立指向仓库内 Skill 的符号链接；实际文件只在仓库中维护。以下命令在仓库根目录执行，目标位置应尚不存在：

```bash
mkdir -p ~/.agents/skills
ln -s "$PWD/skills/ktd-locate" ~/.agents/skills/ktd-locate
ln -s "$PWD/skills/ktd-reconstruct" ~/.agents/skills/ktd-reconstruct
```

调用示例：

```text
$ktd-locate 为什么我读代码能看懂每个方法，却很难理解整个系统的设计？
$ktd-reconstruct 我知道缓存能加速读取，但为什么会引出缓存一致性问题？带我从简单做法开始推导。
```
